# Architectural Strategy & Engineering Roadmap: Eliminating Mock Datasets & Transitioning ShelfBridge to a Fully Backend-Driven, Real-World Data Architecture**Role:** Senior AI & Backend Systems Architect**Author:** ShelfBridge Engineering Team**Date:** October 2026 | AMD Developer 3 Hackathon (`Reinvent Commerce`)**Target Repository:** `ShelfBridge` (Root Directory)---## 1. Executive Summary & Problem Diagnosis### Current Architecture GapAn exhaustive codebase audit of `ShelfBridge` confirms an architectural decoupling between the user interface and domain persistence:1. **Frontend (`Frontend/src/App.jsx`)**: Primarily operates on an **in-memory React state machine** initialized with static constants (`INITIAL_STORES`, `INITIAL_CATALOGUE`, `INITIAL_INVENTORY`, `INITIAL_REQUESTS`). Except for `/health` and `/api/amd-benchmark`, UI actions (creating a request, filtering candidates, confirming offers, creating atomic reservations, verifying handover OTPs, adjusting inventory, and onboarding partner stores) mutate local JavaScript arrays. Browser refresh resets all states.2. **Backend (`backend/`)**: Implements an **ACID-compliant relational domain model** (`SQLAlchemy 2.0`, `FastAPI`, `Pydantic v2`) with 10 database tables, 4-tier deterministic specification parsing and BM25 lexical ranking, atomic inventory reservations, handover verification, and settlement ledger math. It passes all 10 unit/integration tests and an end-to-end live HTTP transaction test.3. **Domain & Data Mismatch**: The frontend models a 3-store cluster in **Nehru Place, New Delhi** using camelCase keys (`onHand`, `typicalTransferPrice`, `requiredSpecs`), while the backend models a 4-store cluster in **Indiranagar, Bengaluru** using snake_case schemas (`stock_quantity`, `transfer_price`, `attributes_json`).### Strategic ObjectiveTransform ShelfBridge from a dual-reality system (simulated client state + separate functional backend) into an **integrated, reactive, backend-driven commercial coordination network** powered by real-world electronics datasets and live database synchronization.---## 2. Concurrency & High-Availability Architecture### A. SQLite (Local Demo) vs. PostgreSQL (Production Multi-Store)To support hundreds of concurrent store queries and prevent overselling during flash demand:```[ Store A Counter Terminal ]          [ Store C Mobile Scanner ]             │                                     │             ▼                                     ▼     POST /api/offers/1/accept             POST /api/offers/2/accept             │                                     │             └──────────────────┬──────────────────┘                                ▼               ┌─────────────────────────────────┐               │    PostgreSQL Engine (ACID)     │               │  BEGIN TRANSACTION ISOLATION    │               │  LEVEL REPEATABLE READ;         │               │  SELECT * FROM inventory_items  │               │  WHERE id = 'inv_102'           │               │  FOR UPDATE;                    │               │  -- Evaluates unreserved stock  │               │  -- Commits reservation         │               │  COMMIT;                        │               └─────────────────────────────────┘```1. **Local Mode (SQLite)**: SQLite handles concurrency via file locks (`BEGIN IMMEDIATE`). As verified in our audit, competing writes are serialized.2. **Production Mode (PostgreSQL with Row-Level Locking)**:   - Configured dynamically via `DATABASE_URL=postgresql://user:pass@host:5432/shelfbridge`.   - Uses `SELECT ... FOR UPDATE` on the specific `inventory_items` row.   - Prevents table-level lock contention so independent store transactions proceed in parallel without blocking.---## 5. Verification & Acceptance CriteriaA fully backend-driven ShelfBridge deployment is accepted when:1. **Zero Mock Arrays**: Deleting `INITIAL_STORES`, `INITIAL_CATALOGUE`, `INITIAL_INVENTORY`, and `INITIAL_REQUESTS` from `App.jsx` does not break any page or workflow.2. **True Persistence**: Logging a stockout request in Shop A, opening an incognito browser window as Shop B, and completing an offer causes both browser sessions to synchronize through the backend database.3. **Double-Booking Rejection**: Two concurrent browser tabs attempting to reserve the last available unit of a charger result in one receiving an HTTP 200 (Reservation Active) and the other receiving an HTTP 409 (Stock Depleted).4. **Deterministic Accounting**: Financial summary cards reflect the sum of persisted `transaction_outcomes` table records rather than client-side slider approximations.---*Report saved to root repository: `STRATEGY_BACKEND_DRIVEN_ARCHITECTURE.md`.*
